# Enterprise Disaster Recovery & Migration Rollback Policy (P1-016)

## 1. Executive Summary & SLAs

This document defines the authoritative Disaster Recovery (DR), point-in-time snapshot, and schema migration rollback policy for the SSK Footwear Manufacturing ERP system.

### SLA Targets
- **Recovery Time Objective (RTO):** $\le 60\text{ minutes}$ (maximum duration to restore full operational capability after catastrophic outage).
- **Recovery Point Objective (RPO):** $\le 15\text{ minutes}$ (maximum allowable data delta in catastrophic failure).

---

## 2. Backup Architecture & Snapshot Schedule

### Schedule
1. **Daily Full Cold Snapshot:**
   - **Trigger:** Automated cron at `02:00 UTC` daily.
   - **Scope:** Complete database archive covering all collections with SHA-256 cryptographic manifest.
   - **Retention:** 30 days active rotating storage; 12 monthly cold archives.
2. **Hourly Point-in-Time Incremental Backups:**
   - **Trigger:** Every 60 minutes (`00 * * * *`).
   - **Scope:** Delta transactions, inventory movements, ledger writes, and outbox logs.
   - **Retention:** 7 days rolling.
3. **Pre-Deployment / Pre-Migration Snapshot:**
   - **Trigger:** Required prior to applying any database schema migration or major deployment.

### Storage Locations
- Primary snapshots are mirrored immediately to durable secondary object storage (`S3` / cloud vault) in an isolated, multi-region storage class with immutable object locking (WORM: Write Once, Read Many).

---

## 3. Cryptographic Verification & Backup Integrity

Every snapshot generated by `backend/db/backup_restore.py` outputs a structured `manifest.json`:
- Collection name
- Document record count
- SHA-256 cryptographic checksum of the compressed `.json.gz` payload
- Timestamp and schema version

### Automated Verification Command
Run scheduled verification drills to guarantee backup integrity:
```bash
python backend/db/backup_restore.py --verify ./backups/snapshot_20261020_020000
```
If checksum or document count mismatches, the utility exits with code 1 and triggers high-priority alerts to on-call infrastructure engineers.

## 4. Disaster Recovery & Point-in-Time Restore Runbook

### Emergency Restore Procedure (Catastrophic Loss)

1. **Stop Application Ingress:**
   - Divert ingress traffic to the maintenance page to prevent incoming mutations:
     ```bash
     kubectl scale deployment ssk-erp-backend --replicas=0
     ```
2. **Identify Target Point-in-Time Snapshot:**
   - Locate the most recent verified snapshot directory in storage.
3. **Execute Integrity Verification:**
   ```bash
   python backend/db/backup_restore.py --verify /var/backups/target_snapshot
   ```
4. **Restore Database:**
   - Run restore with clean slate option:
     ```bash
     python backend/db/backup_restore.py --restore /var/backups/target_snapshot --drop
     ```
5. **Run Sanity & Integrity Check:**
   - Run database ping and collection validation:
     ```bash
     python -m pytest backend/tests/test_audit_fixes_comprehensive.py -k "test_healthz"
     ```
6. **Resume Application Traffic:**
   ```bash
   kubectl scale deployment ssk-erp-backend --replicas=3
   ```
7. **Post-Restore Audit:**
   - Confirm audit logs recorded the restore event (`action: restore_backup_drill`).

## 5. Schema Migration Rollback Procedures

Migrations in `backend/db/migrations/runner.py` use forward-only numbering with distributed locks (`global_migration_lock`).

### Scenario: Migration Failure or Post-Migration Regression

1. **Check Migration Lock Status:**
   - Inspect lock state:
     ```bash
     python -c "import asyncio, server; asyncio.run(server.db.migration_locks.find_one({'_id': 'global_migration_lock'}))"
     ```
2. **Rollback Migration Version:**
   - To roll back a problematic migration (e.g., version `005`):
     ```bash
     python backend/db/backup_restore.py --rollback-migration 005
     ```
   - This automatically:
     - Removes version `005` and any higher records from `schema_migrations`.
     - Releases the distributed migration lock.
     - Logs the rollback incident with timestamp and reason.
3. **Compensating Script Execution:**
   - If schema structural alterations occurred (e.g., new unique indexes preventing valid legacy records), drop the specific index or execute the inverse migration script.
